# Code-provider rules

These are the exact rules, bounds and formats behind CODE-001 in [CONTRACT.md](../../CONTRACT.md). The contract holds the requirement and its acceptance; this page holds the mechanism they rely on, as recorded when the contract was rewritten to the RER contract standard on 28 October 2026.

**Current GitHub slice (22 October 2026):** Owner-selected repositories retain merged pull requests with their head and merge revisions, all returned approval/rejection/dismissal events with the review's own commit and timestamp, check runs and commit statuses on the exact head revision, and deployments with source outcome and time. A deployment links to a change only on the exact merge revision and when it occurred after that merge. Current check results never establish their historical state at merge; unmatched deployments, missing history, unavailable classes and empty histories remain explicitly unknown. The bounded reader admits at most 20 merged changes and 20 deployments per repository, 50,000 bytes of retained history per repository and 80,000 across a connection; an excess is a named gap, never clean assurance. Source paging uses COLLECTION-001's authority-bound durable journal. Original history stays with the collection/control/audit-period snapshot and survives custody restore without reactivating authority. Only consumed metadata is retained, excluding PR bodies, check output, deployment payloads and arbitrary provider fields. GitHub memberships, administrator membership and the authorized two-factor-disabled list feed Identities and Inventory; organization enforcement is a separate fact from individual enrollment. A login never creates or matches a person. Owner-approved People matches establish departure comparisons; any unmatched membership keeps that coverage unknown. A denied membership read retains known accounts as unread, while a fresh source removal retains its prior versions. The GitHub-generated SPDX 2.3 dependency export feeds package inventory, including AI SDK names for AI-001; its unknown manifest revision, absent original manifest files and historical completeness remain labeled. Package presence is not AI-tool approval. Dependency, secret-scanning and membership reads remain read-only. No live-provider verification is claimed.

**Current GitLab and Bitbucket slices (22 October 2026):** GitLab binds the authorized group’s immutable id; a replacement group cannot inherit the old authority. Selected projects collect private/internal/public visibility, protected default branches, applicable approval-rule minimums, required successful non-skipped pipelines, merged requests, current approvers, detailed exact-head pipelines, deployments and package metadata. The required-review number is the maximum applicable rule minimum, a lower bound rather than a sum of overlapping rules. Current approvers do not establish a reviewed commit or approval time. A deployment status without a source update time stays current-only; its creation time is never substituted. Inherited membership is reviewably matched to People and compared with departures; individual MFA enrollment and last sign-in stay unknown, separately from group enforcement. Unsupported licensed vulnerability/secret classes retain their manual replacements.

Bitbucket binds the immutable workspace id, keeps each selected repository’s privacy and branch restrictions, and counts approval/build requirements only when merge checks are enforced. A branching-model matcher the reader cannot resolve is an explicit gap. Merge time comes from the unique MERGED activity event, never a later pull-request update; source precision and offsets are retained, and sub-millisecond ordering cannot invent a deployment-after-merge link. Approval activity has an unknown reviewed revision. Commit statuses use the exact source head. Pipelines deployments retain exact release revisions, actual pipeline readback and its separate outcome (including contradictions), and owner-reviewed production-environment mappings. Classification needs the latest exact source snapshot and a reason, applies prospectively, and never rewrites an old report. Workspace memberships retain unknown active/MFA state; explicit People matches govern departure comparisons. A parsed package.json feeds SDK inventory at its exact source revision, without scripts or arbitrary fields; other formats and original bytes beyond the separate manual root-path custody door remain unproved. Both providers inherit COLLECTION-001 schedules, source-event permissions, durable cursors, original failed outcomes, audit-period context and inactive restore, and INVENTORY-001’s retained source rows and owner decisions.

**Current source-finding slice (c31):** GitHub dependency and secret-scanning alert metadata feed the owner Vulnerabilities source-finding list, `/api/vulnerabilities/source-findings` and Inventory as connection-qualified `code.finding` records. Filtered alert counts and detailed feed counts are separate source answers; disagreement retains both counts and makes the catalogue result unknown. Each class validates the official source identity, state and timestamps before any durable checkpoint; dependency records retain severity, package, ecosystem, CVE and GHSA metadata. Literal secrets, locations, advisory prose and resolution comments are excluded. Reads are bounded to 500 findings per class/repository and 1,000 per connection, with an explicit gap on excess. Earlier source versions remain; an unreadable, malformed or no-longer-returned alert stays unknown rather than being removed or verified closed. Failed, unfinished, revoked, restored or stale source coverage is unknown in the source list. Fixed, dismissed and resolved are provider statements only; the manual penetration-test retest/closure path is unchanged. VULN-001 inherits this source register for its future triage, SLA and independent retest lifecycle. Other providers’ normalized finding feeds remain unbuilt.

**Current Azure DevOps slice (22 October 2026):** Owner-selected Azure Repos use immutable project and repository ids, with a separately bound organization address and human-readable labels. Privacy, enabled blocking policies scoped to the selected default branch, required reviewer lower bounds and required build/status checks are collected. The creator vote is excluded from the reviewer lower bound when the policy allows it. Completed changes retain head and merge revisions; current reviewer votes never invent an approval time or reviewed commit. Exact-head statuses remain distinct from historical merge assurance. A classic Pipelines deployment links only after its release artifact and actual build both identify the selected repository and exact merge revision; deployment and build outcomes stay separate. Unavailable completion times and unmatched production changes are unknown. Production classification requires the latest observed environment snapshot, owner review and a reason, applies prospectively and never rewrites older history. Graph subjects require explicit People matches; unexposed activity, administrator and MFA facts remain unknown. A package.json read at an exact commit feeds package/SDK inventory without scripts or arbitrary fields. Selected reads, paging, events, failures, context, period reports, inventory and inactive custody restore use the same current-door obligations as the other code providers. No live-provider verification is claimed.
