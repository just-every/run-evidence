# Operating Evidence

Use the documented `rer setup`, `rer dev`, `rer build` and deployment commands in README.md and SEED-COMMAND-CONTRACT.md. This page describes the OPS-001 runtime slice; it does not claim the full operational acceptance is complete.

Before the private HTTP doors or Cron work touch data, Evidence checks DB, EXHIBITS, AUTH_ORIGIN, OWNER_EMAIL and SESSION_SECRET. Invalid or absent settings produce HTTP 503 with only their setting names. An optional SETUP_TOKEN is checked when supplied. Origin, email and secret-size rules match the existing owner-auth module. Cron refuses the same configuration before claiming work. Provider-specific optional mail configuration remains validated by its existing mail module; complete named-setting coverage there is still a gap.

The owner can read `GET /api/operations` using the same session and same-origin boundary as product audit. It returns the newest 100 scheduled-step attempts, a `more` indicator and the 15-minute claim lease. A step's processed count measures work returned by that step, not successful controls, source coverage or messages delivered. Inspect the underlying collection runs, tickets, observations and follow-ups for those outcomes. Dispatch and finish timestamps use the Cron dispatch clock; they do not measure elapsed execution time.

A step records its claim in D1 before invoking work. Only one running attempt per step can hold the claim. It records success or failure on completion; raw exception messages are excluded. A failure to persist the final outcome fails the Cron event and retains the running claim. After its inclusive 15-minute lease boundary, the next tick changes an unfinished attempt to Unknown. Terminal outcomes cannot be changed or deleted. Replayed Cron events recheck the existing durable product queues; the queues retain their own deduplication identities. An Unknown attempt is never rewritten as success, and recovery does not invent source observations.

Delivery recovery checks at most 100 expired pending follow-ups per tick, oldest first. A pending delivery at least 15 minutes old becomes uncertain with a product-audit entry. It is never automatically resent, because the provider may already have accepted it. The existing follow-up resolution door lets the owner record later confirmation. A provider response received after this reconciliation must not overwrite that uncertain outcome.

Execution metadata in `operation_steps` belongs to this installation and survives Worker restarts. It is explicitly excluded from portable evidence custody archives; it is not a source observation or a product obligation. Keep the underlying product history and complete original-byte custody archive for recovery. Operational history backup/restore is not yet implemented. The owner health screen, measured storage/queue limits, complete backup status, independently interrupted-worker acceptance and bounded/cancellable underlying jobs remain OPS-001 gaps. The claim lease diagnoses lost outcomes; it does not cancel an old worker or fence all of its product writes.

Evidence charges USD 0; optional provider and hosting costs are shown in USD on their existing enablement pages. Existing backup, migration, size-refusal and cost journeys remain required; this slice does not change Base copies or the rer pin.
