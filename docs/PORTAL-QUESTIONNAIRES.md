# Portal questionnaires

The Manifest V3 extension source is in `./public/portal-extension/`. It captures a questionnaire for an owner installation and fills exact approved text, choices and original documents. It never clicks a portal control, emits a change event, navigates to another portal page or submits a form. The user moves between pages and remains responsible for reviewing and submitting the portal.

Load that directory as an unpacked extension from the browser's extension settings with developer mode enabled. The source targets Chrome, Microsoft Edge and Brave. An installed-extension journey in all three browsers has not yet been proved; ANSWER-002 remains partial. The native Chromium journey exercises the shipped scanner and applier, the real three-page test portal and the production approval API at both 1440 and 390. It does not establish all three browsers' extension APIs.

In Evidence, open Connections, then API tokens. Issue a short-lived token with `portal-capture` and `portal-fill` only. The first scope imports questionnaires but cannot read answers; the second releases only current exact approved answers and documents for captures created by that same token. Neither scope approves, publishes or reaches owner doors. The normal API installation binding, digest-only token storage, revocation, expiry and rate limit apply. Restore carries the record and history but no usable token credential. Revoking a token prevents further calls; it cannot retrieve bytes already released to an authorized browser.

Open the extension on the portal. Connect to the Evidence installation origin, enter the token, program ID and questionnaire name, and explicitly grant access to that installation. HTTPS is required except for local loopback installations. Credentials and pending captures stay in extension session storage, never in portal scripts or browser sync. Clear session removes them; closing the browser ends the session. Reconnecting clears previous pending pages. Do not share a token between unrelated capture operators.

Name each page or step and choose Capture current page. The scanner retains labels, sections, stable field identifiers, text, single-choice, multiple-choice, checkbox and file types, allowed options and required attributes. It does not read entered text, selected answers, file bytes, passwords or hidden inputs. A stable identifier is qualified by the containing form. Unnamed fields, unsupported input types, ambiguous identifiers or option values, embedded frames and open shadow roots are reported and block import. Closed shadow trees and custom controls are not supported. A capture supports at most 100 pages, 2,000 fields and 1 MiB; larger questionnaires need separate captures. Page URLs omit query strings and fragments, so a distinct page identifier is required for each step using the same path. All pages must use the same portal origin. Review the page list before import.

Import creates an immutable questionnaire, original capture bytes, capture time and page structure. Open it in Questionnaires. Text drafts quote current authorized sources exactly. Other fields remain flagged until a reviewer explicitly maps a cited passage to the exact option value; a multiple-choice value is a JSON list such as `["security","legal"]`. A standalone checkbox uses the declared `true` and `false` values. For a file field, select an exhibit source with its exact filename as the passage, confirm the document and enter a review reason. A sensitive exhibit must first have explicit owner publication; unavailable or superseded originals cannot be attached. The named reviewer approves the exact latest answer set and recipient, including the document fingerprint. A flagged field receives no fill authority.

Enter the questionnaire ID, approved draft ID, exact recipient and page identifier in the extension. Re-scan and fill approved fields asks Evidence to check the latest exact approval, recipient, expiry, source freshness and customer-promise dependencies. Added, removed, retyped, relabelled or changed-option fields are refused individually. It re-scans again in the isolated content world before assigning each field. Original document bytes are independently checked against the approved size and SHA-256 digest before attachment. Fill never appends citation prose to the buyer's field and never substitutes an unsupported value. Portals that require synthetic change events or framework-specific controlled-field integration are not yet supported; inspect the result before manually continuing.

To re-capture, capture all pages again using the same token, then import. The new questionnaire links to the previous immutable capture and needs its own draft and exact human decision. No earlier approval carries over. Capture and fill history shows the exact revision, plans, refusals, document release and extension-reported field outcomes. A client report is not proof of portal acceptance or submission. If reporting fails after writing fields, inspect the portal before retrying; the extension explicitly reports that uncertainty. Closing the popup mid-fill may prevent a client outcome from being recorded; the server's plan and document-release history remain retained.

Questionnaires, captured metadata, source decisions, originals and product audit travel through the existing custody archive. Tokens restore inactive and nothing fills or submits on restore. New extension capabilities inherit the existing AUTH-001, SECURE-001, LOG-001, PORTABLE-001 and AGENT-005 gates.
